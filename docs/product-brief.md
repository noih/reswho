# reswho 產品方向

## 狀態

本文件記錄產品方向。macOS 唯讀採集原型已實作，詳見 [採集驗證](collection-probe.md)；已加入 TCP／UDP 端點與通用結構分類；TUI、容器內部採集與 Review 尚未實作。以下完整第一版範圍不代表已完成。

## 已確認方向

- 名稱為 `reswho`，採 TUI，產品介面可全英文。
- 第一版平台為 macOS，使用 Rust＋Ratatui，採集層與呈現層分離。
- 第一版唯讀，不提供停止程序、停止容器或刪除資料的操作。
- 保留 top 類工具的通用監控優點，加入資源歸類、來源辨識與遺留服務檢查。
- 樹狀呈現分類及從屬關係，支援逐層展開。
- 分類由粗到細：即使無法確認專案，仍可辨識為 Docker、應用程式、開發程序或系統服務。
- 不要求完全正確的專案歸屬；無法確認時保留原始資訊、線索及不確定性。
- 以既有線索立即提供價值，不要求使用者透過 reswho 啟動工作或預先保存啟動紀錄。
- 除了高用量程序，也必須找得到低用量、甚至 CPU 為零但可能忘記關閉的服務。

## 使用者要解決的問題

1. 目前哪些應用、容器、服務與專案在使用資源，各用了多少？
2. 多個同名的 node、Python 或資料庫程序，分別在做什麼、位於哪個路徑？
3. 哪些背景服務可能已完成用途，卻仍保留監聽埠或附屬程序？
4. 有哪些證據支持歸屬或遺留判斷？
5. 某個工作包含哪些相關程序或容器？停止操作留待後續版本。

## 歸屬線索

| 線索 | 可提供的資訊 |
| --- | --- |
| 工作目錄、專案描述檔、Git 根目錄、common directory 與 worktree | repository 與 checkout 身分 |
| 執行檔、完整命令及腳本路徑 | 應用、runtime、服務角色與可能專案 |
| App bundle 路徑與宣告的 bundle ID | 跨安裝路徑／暫存副本的應用分組；內層保留路徑 |
| 父子程序 | 啟動工具與附屬程序；父程序已退出時可能不完整 |
| 容器 name、labels、mounts、Compose metadata 等可用資訊 | 容器角色、專案候選與主機路徑 |
| 開啟檔案、日誌路徑 | 補充來源線索；不代表必然歸屬 |
| 監聽埠與連線 | 服務關係與可觀測活動 |

分類使用通用、可驗證的結構與 metadata，不依賴特定電腦的 app／process 名稱清單。缺乏線索時保留粗分類或未知，並區分直接觀測與推論。

分類優先順序為直接 App → 直接 Project → 經條件驗證的祖先歸屬 → Bin → Unknown。System 依系統路徑保留大分類，其內亦可按 bin 彙總。非 Git 專案依最近的描述檔辨識，支援標記見 `collection-probe.md`。沒有標記時保留 cwd，不猜用途。

分類須附依據。名稱前綴屬弱線索；工作目錄或 mount 能提供較直接的路徑關聯。相同文字出現在 name 與 label 時，不應當作兩份獨立證據。線索衝突時呈現候選或未知，不強制選擇。

同一個 Git common directory 下若有多個 checkout 在執行程序，顯示「repository → checkout → project → process」，位置重合的 checkout／project 共用一列。內層保留完整路徑與原 ref；只有一個 checkout 時省略 repository 父層。同名但獨立 clone 的 repository 不合併；metadata 不可讀時保留 checkout 原分組。

歸屬與目前是否需要服務是不同問題。辨識出專案，不代表能安全判定該服務可以停止。

herdr、playwright-cli、Chrome 等先由執行檔、命令列、應用路徑與父子程序等通用線索辨識，不預先要求每個工具都有專用整合。父子關係不等於同專案；同名應用也不代表同一實例。

容器模型須容納 Docker、Podman 與 Apple container；實際可取得資訊與首版 adapter 範圍由採集驗證確認，不將尚未驗證的支援視為完成。

## 輸出模式與深入查詢

現行 Markdown 層級、欄位與狀態符號見 [Markdown 輸出格式](markdown-format.md)。

| 指令 | 行為 |
| --- | --- |
| `reswho` | stdin／stdout 都是終端機時使用 TUI，否則輸出一次性 Markdown |
| `reswho --tui` | 明確啟用 TUI；無可用終端機時回報錯誤 |
| `reswho --md` | 一次性 Markdown，供 AI 閱讀 |
| `reswho --json` | 一次性 JSON，供程式處理 |
| `reswho --help` | 指令與選項說明 |
| `reswho --help-format` | Markdown 欄位順序、單位、符號與範例 |

三種明確輸出模式互斥，共用資料與判斷；非互動輸出不等待操作、不持續刷新，不輸出終端機控制碼。診斷與資料輸出分離。

Markdown 使用 `#` 報告標題、`##` 大分類與一般段落摘要；其他資源維持巢狀清單。名稱與 ref 使用一般文字，避免固定欄位的冗餘修飾；路徑使用行內 code 保護字面值，群組附分類標籤；程序名稱完整保留。屬性、證據與診斷使用縮排引用區塊，不當成子節點。單一程序的 bin 省略群組層，直接顯示 PID。巢狀清單表示資源層級，採固定、精簡、可查閱的格式，不要求每項資訊皆為 key/value。程序摘要欄位順序為 `[name] · [ref] · [cpu] · [memory] · [uptime] · [ports]`；`-` 表示確認沒有，`?` 表示未知或無法取得，數值直接附單位。缺值保留位置；證據、路徑與例外放在下一層。群組、程序與容器行須可區分，完整格式在實作時定義並提供版本識別。

- `--from pid:6481`：從指定程序深入查看。
- `--from group:<id>`：從指定分類、應用、專案或容器分支深入查看，不要求理解各 runtime 原生 ID。
- `--depth N`：起點為第 0 層；1 表示顯示起點與直屬子項。`--depth all` 完整展開，預設 2 為目前設計建議。
- 一般 Markdown 展開每程序一行；指定 `--from pid:N` 時，只有選取的程序顯示 PPID／UID、路徑、socket、歸屬與不可用原因，子程序仍為摘要。
- 完全無可讀資料的程序合併成 `Unreadable · N processes`，無 ref 或展開箭頭；部分可讀、零用量與無法歸類的程序仍保留。JSON 與明確 PID 查詢保留原始資料。
- 每個一般節點保留可複製的 ref；收合時僅在原列加 `▸`，不重複程序數量。展開指令集中在 `--help-format`，不逐項重複。
- 群組摘要顯示 `oldest 2h`，代表組內最久存活程序的啟動至今時間（包含閒置），不是群組存續時間或累計使用時數；部分未知時顯示 `oldest >=2h`，全部未知為 `oldest ?`。
- `!` 僅標示當次採集錯誤／限制，`~` 僅標示有來源與條件的推論附註；一般限制集中在 help，PID 詳情保留原始錯誤。
- 深度只限制呈現，標題／段落／引用不佔深度，不改變群組統計範圍；分類成員與程序父子關係須區分。
- group ID 不使用顯示序號或分類位置，須在相同資源的跨次查詢保持一致，內部區分 runtime、端點與原生身分。
- 目標不存在時明確回報，不改配同名資源。PID 查詢取得當前程序；程序持續追蹤需搭配啟動身分辨識 PID 重用。

## 遺留服務檢查

以多項跡象提供待檢查排序，不自動宣告程序可刪除：

- 短期用途的程序存活很久，例如臨時預覽、測試容器、TLS probe。
- 同一專案有多份相似服務。
- 啟動者已消失，但服務仍存在；需考慮正常背景化情境。
- 工作目錄或對應 worktree 已不存在。
- 觀測期間缺乏連線、CPU 或 I/O 活動。

單次掃描只能描述當下。只有實際累積觀測，才能顯示一段時間的無活動；取樣可能漏掉短暫連線。權限不足或資料缺失須標示 unknown/unavailable，不能當成零活動。

## 第一版範圍

- macOS、Rust＋Ratatui、唯讀。
- 基本 CPU、memory、swap 概況與程序列表，支援排序、搜尋及詳情。
- 分類資源樹，顯示應用、Docker、專案／worktree 與未知項目。
- `Overview`、`Processes`、`Review` 與 `Details` 視圖。
- 顯示 PID、執行時間、路徑、命令、埠與可用的歸屬線索。
- 低用量服務不因用量排序或閾值而從 Review 消失。
- TUI、精簡 Markdown 與 JSON 三種輸出，支援指定分支與展開深度。

視圖細部配置、採集成本、權限限制與容器 adapter 支援範圍，仍須以小型採集驗證確認。

## 統計與互動原則

- 指標口徑一致且明確；程序 CPU 與整機 CPU 的百分比基準須區分。
- 每個程序在同一統計範圍只計算一次；同一資源出現在不同視圖，不代表可再次加總。
- Docker VM 的主機用量與容器內部用量分屬不同統計範圍，不重複加總，也不直接相減來推算精確開銷。
- 未知、權限不足及觀測尚未完成的數值，不顯示為零。
- 刷新與排序時維持選取目標身分；PID 重用不能讓操作指向新程序。
- 不自動停止疑似遺留項目。停止服務不等於刪除容器、volume 或資料。
- 不將原始命令列、環境變數等可能含秘密的資訊無條件保存或輸出；具體遮罩規則待設計。

## 尚未納入第一版的建議

停止資源操作留待後續版本。完整 GPU、溫度、功耗與磁碟／網路圖表，以及 agent thread 的專屬整合，先留待需求確認。AI 與啟動包裝指令可作補強，不作為基本分類的必要依賴。
